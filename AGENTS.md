# AGENTS.md

A safer replacement for sharp in Next.js: decode (untrusted) → auto-orient/rotate → resize → encode. A sharp-like TypeScript wrapper sends each image to a pool of workers: native worker processes (managed by a small napi-rs binding), or worker threads running a wasm build.

## Layout

A Cargo workspace:

- `crates/core` (`blunt-core`): everything that touches images. Only ever runs in a worker.
  - `protocol.rs`: the request/response format (the other side is `js/protocol.ts`), and worker exit codes. `request.rs`: request options. The JS wrapper passes most of them through as the caller wrote them, so this is where they're validated, including unknown fields. The wrapper throws its errors (`ERR_INVALID_OPTIONS`) as `TypeError`s. Items marked `#[typeshare]` (request options, `InputFormat`, `ErrorCode`, and constants) are exported to `js/protocol.generated.ts`.
  - `pipeline.rs`: stage order. Resizes *before* rotating (cheaper), so `orientation.rs` maps targets back to the input frame (crops are always centered, so they're the same in either frame). ICC → sRGB (`color.rs`, moxcms) runs after resizing.
  - `decode/`: one file per format. `encode/`: one file per format. `ops.rs`: resize (`image::imageops`, with alpha premultiplied around it). Only what Next.js uses: sharp's default `fit: 'cover'` (centered), plus `kernel`, `withoutEnlargement`, and `withoutReduction`.
  - `limits.rs`: memory limits. `alloc.rs`: `ExitOnOom`, the workers' global allocator.
- `crates/worker` (`blunt-image-optimization-worker`): the worker process. Reads requests from stdin, writes responses to stdout. Sandboxed with seccomp on Linux. With `--fork-server` (unix), it forks workers instead (`fork_server.rs`).
- `crates/wasm`: the same, as a `wasm32-wasip1` module with raw exports (no wasm-bindgen, no napi).
- `crates/scm` (`blunt-scm`, unix only): sending file descriptors over Unix sockets, shared by the shim and the fork server.
- `crates/shim`: the napi binding. Only spawns and talks to workers, with no image code. One driver thread per live worker, plus a watchdog thread for timeouts, and on unix, a thread per fork server (`fork.rs`).
- `vendor/avif-decode/`: git subtree of [avif-decode](https://github.com/kornelski/avif-decode), patched to disable rav1d's asm, use rav1d's Rust API, and take thread and frame size options. Commit upstream updates with `git subtree pull --squash`.
- `js/index.ts`: public API (compiled to `dist/` by `pnpm build:js`). `js/native.ts` and `js/wasm.ts` are the two backends, and `js/wasm-worker.ts` runs in each wasm worker thread.
- `binding.js`, `binding.d.ts`: generated by napi, but committed. CI fails if they're stale.
- `js/protocol.generated.ts`: generated by [typeshare](https://github.com/1Password/typeshare) (`pnpm generate`, configured by `typeshare.toml`), but committed. CI fails if it's stale. typeshare exports unit enums as TS enums, so `js/index.ts` derives the public string unions from them (`` `${generated.Fit}` ``), and `typeshare.toml` maps fields to those unions too. It can't export externally tagged enums (`Request`) or string constants.
- `test/*.test.ts`: e2e tests (`node --test`, native type stripping).
- `turbo.json`: `pnpm build` and `pnpm build:release` run the native and JS builds in parallel with turbo, which caches `build:js` (cargo caches the native and wasm builds itself). Builds default to debug; only scripts suffixed with `:release` produce release builds. `build:js` compiles against the committed `binding.d.ts`, so after changing the shim's API, run `pnpm build:native` first. CI runs build tasks through turbo.
- `scripts/build-native.mjs`: builds the shim (with `napi build`, in a scratch directory) and the worker, and copies them to the root.
- `scripts/build-wasm.mjs`: builds the wasm module, and checks its imports against an allowlist (the stubs in `js/wasm-worker.ts`).

## Rules

- Never decode with C libraries. libwebp and mozjpeg are only for encoding.
- Disable `default-features` and enable exact features for dependencies.
- Never ship two copies of an image library. resvg decodes embedded images with its own direct dependencies on zune-jpeg, png (via tiny-skia), gif, and image-webp, which must resolve to the same versions as `image`'s. When upgrading `image` or resvg, upgrade the other to match. `decode::svg::tests::image_crates_are_deduplicated` checks `Cargo.lock`.
- Import with `crate::` paths, not `super::`. The only exception is `use super::*;` in `mod tests`.
- Validate options in `request.rs`, not in `js/index.ts`, unless the wrapper uses them itself (pool options, `timeout()`, `limitAllocatorMemory`).
- Images are always 8-bit `Luma8`/`LumaA8`/`Rgb8`/`Rgba8` after `decode::normalize`.
- Rely on the worker's memory limits and the caller's timeout, instead of configuring each decoder defensively. Only the pixel limit is checked up front. Anything allocated outside Rust (libwebp, mozjpeg) needs its own check against `Limits`.
- Workers are untrusted. The shim and the JS wrapper validate every response, and kill a worker that sends a malformed one. Each worker handles one request at a time.
- Workers are built with `panic = "abort"` (the `worker` and `worker-dev` profiles), so there's no `catch_unwind`. A panic, abort, or out-of-memory exit only ends the worker. Keep `crates/shim` panic-free: it runs inside Node.
- After changing a `#[typeshare]` item, run `pnpm generate` (needs `cargo install typeshare-cli --version 1.13.4 --locked`). The binary response format isn't generated, so keep `crates/core/src/protocol.rs` and `js/protocol.ts` in sync by hand, and the exit codes in `crates/shim/src/pool.rs` (which doesn't depend on `blunt-core`).
- Tests generate fixtures with sharp. Never commit images. Compare against sharp for parity (dimensions exactly, pixels approximately).
- Before changing CI, read `.github/AGENTS.md` (pinned SHAs, `permissions: {}`, corepack, etc).

## Workers

- **Spawning:** the shim spawns workers with `<version> <parent pid> <memory limit>` arguments (the worker exits with `EXIT_VERSION_MISMATCH` if the version differs), an empty environment, and piped stdin/stdout. stderr is inherited in debug builds, and discarded in release builds.
- **Fork server (unix):** by default (`forkServer` in the binding's `PoolOptions`), each pool spawns one worker with `--fork-server` and a Unix socket as stdin, which forks the pool's workers (skipping `exec` and loading the binary). The shim sends each worker's pipes with `SCM_RIGHTS`, plus a status socket, where the server reports the pid (with a pidfd on Linux 5.3+) and, after reaping the worker, its wait status. The watchdog kills with the pidfd, or else through the server, which only signals workers it hasn't reaped. The server's replies time out (`SERVER_TIMEOUT`), and the shim abandons a server that's stuck. The server is single-threaded and never sees image data, and workers close every fd it holds. The server itself has no seccomp filter (workers install theirs after forking). A filter for it would have to allow everything a worker does before its own filter is on (`clone`/`clone3`, `prctl`, `seccomp`, `dup3`, `rseq`, etc., varying by architecture and libc), for little benefit: it only reads messages from the shim, and workers can't reach it. The shim restarts a server that exits. Forked workers share the server's address space layout (ASLR) and stack canaries (documented in the README). The `native worker failures` tests use shell scripts as workers, so they mostly turn the fork server off.
- **Parent death:** a reader thread in the worker exits the process as soon as stdin closes, even mid-request. On Linux, `PR_SET_PDEATHSIG` also kills the worker when the thread that spawned it exits: its driver thread (which must outlive it), or for forked workers, the fork server, whose own thread waits for it to exit.
- **seccomp (Linux x86_64/aarch64):** after startup, only I/O on existing fds, memory management, futexes, and aborting are allowed. `tgkill` (for glibc's `abort`) is only allowed on the worker's own pid, so a compromised worker can't signal Node or the fork server. Anything else fails with `EPERM`. The filter uses `TSYNC`, after the reader thread has started (glibc's thread setup needs `rseq` and `set_robust_list`). If a decoder starts needing a new syscall, it'll show up as a confusing error, not a crash.
- **Memory limits:** `ExitOnOom` counts live Rust allocations. While a request runs, it exits with `EXIT_MEMORY_LIMIT` (reported as `ERR_LIMIT_EXCEEDED`) if they exceed the request's `limitAllocatorMemory`, which includes the request buffer itself. Between requests, there's no limit, because the next request is read before its limit is known. libwebp and mozjpeg (C) allocate with `malloc` directly, so only the hard limit sees it: the pool's `limitProcessMemory`, which the worker applies as `RLIMIT_DATA` at startup (Linux only: macOS's `RLIMIT_DATA` counts reserved address space, so any useful limit fails), or the wasm memory's maximum. When an allocation fails (including `try_reserve`), `ExitOnOom` exits with `EXIT_OUT_OF_MEMORY`. On wasm, exits go through `proc_exit`.
- **Timeouts:** start when a worker picks up a request (not while it's queued). The watchdog kills the worker, which also unblocks the driver's pipe I/O.
- **wasm:** each instance runs in its own worker thread, imports its memory (so JS sets the maximum), and is discarded after a trap, `proc_exit`, or timeout.

## Decoders

Memory is bounded by the worker's limits (`limitAllocatorMemory` in the allocator, `limitProcessMemory` from the OS), and CPU by the caller's `timeout()`. So decoders aren't configured defensively: the only check before decoding is the pixel limit (`Limits::check_input_pixels`), which works the same way for every format.

Every raster format is detected by `image`'s `ImageReader` (`decode/mod.rs`), from magic bytes. The detected format must be in an explicit allowlist (`InputFormat::from_image_format`): `image` also detects formats like BMP and QOI, and Cargo's feature unification means another crate could enable their decoders. Only if `image` detects nothing do we check for SVG. Then the format is checked against the caller's `allowedInputFormats`. `decode::raster_decoder` constructs the decoder itself (like `ImageReader::into_decoder`, but only for our formats), with `limitAllocatorMemory` as `image`'s `max_alloc`. With `allowAnimated: false`, it rejects animations before decoding any pixels, using `PngDecoder::is_apng` and `WebPDecoder::has_animation`, `avif::has_sequence_brand` (avif-parse rejects sequences as unsupported, so this runs first), and `gif::has_second_frame` (`GifDecoder` can only find a second frame by decoding it, so this scans with the `gif` crate, without LZW decoding).

- **JPEG (zune-jpeg), PNG, GIF, WebP, TIFF:** `image`'s built-in decoders. GIF frames always decode as RGBA, so we drop the alpha channel if the first frame is opaque. `image`'s TIFF decoder doesn't support YCbCr, which is how sharp and most encoders write JPEG-compressed TIFFs.
- **AVIF (vendored avif-decode → avif-parse + rav1d):** not `image`'s AVIF decoder, which is dav1d (C). `decode/avif.rs` is an `ImageDecoder` wrapper, and registers a detection hook (checked before `image`'s own signatures, which miss sequences and large `ftyp` boxes). avif-decode is patched with `decode_into`, so it decodes straight into `image`'s buffer, without a copy. rav1d is a git dependency on an unreleased revision for its Rust API. One thread (decoding happens on the calling thread, nothing is spawned on wasm), and the decoded size must match the sequence header. rav1d logs errors to stderr (`rust_api::Settings` can't disable its logger), which release builds discard.
- **SVG (resvg → usvg + tiny-skia):** detected like libvips (`<svg` in the first 1000 bytes, after valid UTF-8). Like sharp, it's rendered at 72 DPI, as RGBA, and at the size it's being resized to (`ops::vector_scale`), not resampled from its natural size. The pixel limit applies to both the natural and rendered sizes. Built without `text` (no fonts at all: Next.js's OG images come from Satori, which converts text to paths) and `svgz`. `raster-images` renders embedded images (`<image href="data:...">`). **The pixel limit doesn't apply to them**: resvg decodes them itself, during rendering, with no size checks, so they're only bounded by the memory limits and the timeout. A small SVG can embed a huge image. This is documented in `limitInputPixels`'s doc comment and the README, so keep those in sync. usvg's default `<image href>` resolver reads files, so `decode/svg.rs` replaces it with one that only accepts `data:` URLs. On wasm, that dead `std::fs` code still imports WASI filesystem functions, which `js/wasm-worker.ts` stubs out to always fail.

## Encoders

JPEG uses `jpeg-encoder` by default, and mozjpeg (C) with `mozjpeg: true`. mozjpeg's defaults are sharp's mozjpeg preset (trellis quantization, overshoot deringing, scan optimization). It reports errors by unwinding, which aborts the worker, so check anything it would reject (like dimensions over 65500) before encoding.

libwebp and mozjpeg (C) are the only encoders the allocator can't see, so `encode::c_encoder_bytes_per_pixel` estimates their working memory, and checks it against `limitAllocatorMemory` before encoding. The numbers are measured (peak RSS on noisy 16 MP images), so re-measure when changing their settings.

```sh

WASI_SDK_PATH=... pnpm build:wasm && pnpm test:wasm
```

## Gotchas

- **wasm:** wasi-sdk only compiles libwebp and mozjpeg. Rust links with its own bundled wasi-libc. Rust 1.100+ links wasi-libc's reactor startup (an `_initialize` export) and older versions don't, so `js/wasm-worker.ts` calls `_initialize` only if it exists.
- **Linux CI:** builds use cargo-zigbuild (glibc 2.28, matching Node), for both the shim and the worker.
- **CI artifacts** don't keep file permissions, so test jobs `chmod +x` the worker.
- **Publishing:** the worker belongs in each platform package, next to the `.node` file (`js/native.ts` looks there), but `napi prepublish` doesn't know about it yet.
