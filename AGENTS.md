# AGENTS.md

A safer replacement for sharp in Next.js: decode (untrusted) → auto-orient/rotate → resize → encode. A sharp-like TypeScript wrapper sends each image to a pool of workers: native worker processes (spawned by the wrapper, with `node:child_process`), or worker threads running a wasm build. There's no native Node addon.

The npm package is `@next/safe-image-optimization`. Internal names (crates, wasm exports, test environment variables, temp files) use the prefix `nsio`.

## Layout

A Cargo workspace:

- `crates/core` (`nsio-core`): everything that touches images. Only ever runs in a worker.
  - `protocol.rs`: the request/response format (the other side is `js/protocol.ts`), and worker exit codes. Both are JSON plus binary data (the input, or the encoded image), in a frame with the JSON's length. A response's JSON is at most `MAX_JSON_BYTES` (the worker truncates long error messages), and its data at most the request's `limitOutputBytes`, so the parent knows how much it may have to buffer. `request.rs`: request options. The JS wrapper passes most of them through as the caller wrote them, so this is where they're validated, including unknown fields. The wrapper throws its errors (`ERR_INVALID_OPTIONS`) as `TypeError`s. Items marked `#[typeshare]` (request options, responses, `InputFormat`, `ErrorCode`, and constants) are exported to `js/protocol.generated.ts`.
  - `pipeline.rs`: stage order. Resizes *before* rotating (cheaper), so `orientation.rs` maps targets back to the input frame (crops are always centered, so they're the same in either frame). ICC → sRGB (`color.rs`, moxcms) runs after resizing.
  - `decode/`: one file per format. `encode/`: one file per format. `ops.rs`: resize (`image::imageops`, with alpha premultiplied around it). Only what Next.js uses: sharp's default `fit: 'cover'` (centered), plus `kernel`, `withoutEnlargement`, and `withoutReduction`.
  - `limits.rs`: memory limits. `alloc.rs`: `ExitOnOom`, the workers' global allocator.
- `crates/worker` (`nsio-worker`, binary `safe-image-optimization-worker`): the worker process. Reads requests from stdin, writes responses to stdout. Sandboxed with seccomp on Linux (`linux_sandbox.rs`, in the crate's library, so that `tests/linux_sandbox.rs` can install the filters in a child process; it runs without the test harness). With `--fork-server` (unix), it forks workers instead (`fork_server.rs`), and passes their sockets to Node over its IPC channel (`node_ipc.rs`).
- `crates/wasm`: the same, as a `wasm32-wasip1` module with raw exports (no wasm-bindgen).
- `vendor/avif-decode/`: git subtree of [avif-decode](https://github.com/kornelski/avif-decode), patched to disable rav1d's asm, use rav1d's Rust API, and take thread and frame size options. It's a workspace member only because turbo requires it (not a default member, so `cargo test` and `cargo clippy` skip it), so its manifest also allows clippy's lints and has no profiles, and its `rustfmt.toml` disables formatting. Commit upstream updates with `git subtree pull --squash`.
- `js/index.ts`: public API (compiled to `dist/` by `pnpm build:js`). `js/native.ts` and `js/wasm.ts` are the two backends, and `js/wasm-worker.ts` runs in each wasm worker thread. `js/musl.ts` is copied from napi-rs (MIT, with its license header).
- `js/protocol.generated.ts`: generated by [typeshare](https://github.com/1Password/typeshare) (`pnpm generate`, configured by `typeshare.toml`), but committed. CI fails if it's stale. typeshare exports unit enums as TS enums, so `js/index.ts` derives the public string unions from them (`` `${generated.Fit}` ``), and `typeshare.toml` maps fields to those unions too. It can't export externally tagged enums (`Request`) or string constants.
- `test/*.test.ts`: e2e tests (`node --test`, native type stripping). CI compiles them in place (`build:test`) and runs the JS, because it also tests Node.js 20.9 (the oldest version Next.js supports), which can't strip types. So tests can't use APIs newer than that (like `zlib.crc32` or `import.meta.dirname`), and load sharp through `helpers.ts` (its ES module needs Node.js 20.10).
- `turbo.json`: uses turbo's experimental Cargo support (`experimentalCargoWorkspaces`), so each crate is a turbo package, the workspace is `nsio-cargo`, and root `package.json` scripts are `//#<script>` tasks. `pnpm lint` runs `nsio-cargo`'s `lint` (clippy), `format:check`, and `//#typecheck`. `pnpm build` runs the built-in `nsio-worker#build` (`cargo build`, into `target/debug`) and `build:js` in parallel, and turbo caches both. `pnpm build:release` runs `nsio-worker#build:release`, the same with `--release`. Tasks with a `command` lose turbo's built-in Cargo hashing, so that one lists its `inputs`. `envMode` is strict: tasks only see the variables `turbo.json` lists (only ones we set, like CI's `MACOSX_DEPLOYMENT_TARGET` and `WASI_SDK_PATH`), turbo's defaults (`PATH`, `HOME`, `GITHUB_*`, ...), and for built-in cargo tasks, the Cargo and compiler variables turbo adds itself. So add a variable there before a build depends on it. The wasm build goes through a script, which turbo doesn't cache (cargo has its own incremental cache). CI's native builds run `scripts/build-native.mjs` directly, without turbo. Builds default to debug; only scripts suffixed with `:release` produce release builds. CI runs the wasm build and Rust tasks through turbo, but not in test jobs: turbo runs `cargo metadata` before every task, so it needs cargo (and downloads every crate) even for JS tasks.
- `scripts/build-native.mjs`: CI's release builds of the worker (cross-compiled with cargo-zigbuild on Linux), which it copies to the root as `safe-image-optimization-worker.<platform>` (Node's platform name, like `linux-x64-gnu`). `js/native.ts` looks for the worker in `target/debug` or `target/release` (whichever is newer), then that copy, then the platform's package. Local builds and CI's show the worker's stderr, and installed ones discard it.
- `scripts/build-wasm.mjs`: builds the wasm module, and checks its imports against an allowlist (the stubs in `js/wasm-worker.ts`). It copies the module to the root as `safe-image-optimization.wasm`, where `js/wasm.ts` looks for it before the `@next/safe-image-optimization-wasm32` package. It isn't in the main package (like sharp's `@img/sharp-wasm32`), so the default backend only falls back to wasm if that package is installed.

## Rules

- Never decode with C libraries. libwebp and mozjpeg are only for encoding.
- Disable `default-features` and enable exact features for dependencies.
- Never ship two copies of an image library. resvg decodes embedded images with its own direct dependencies on zune-jpeg, png (via tiny-skia), gif, and image-webp, which must resolve to the same versions as `image`'s. When upgrading `image` or resvg, upgrade the other to match. `decode::svg::tests::image_crates_are_deduplicated` checks `Cargo.lock`.
- Import with `crate::` paths, not `super::`. The only exception is `use super::*;` in `mod tests`.
- The API is loosely based on sharp's, but sharp compatibility is a rough guideline, not a rule. Prefer clearer names (with units, like `timeoutMs()` and `limitOutputBytes`) and a smaller API over matching sharp.
- Validate options in `request.rs`, not in `js/index.ts`, unless the wrapper uses them itself (pool options, `timeoutMs()`, `limitOutputBytes()`, `signal`) or the worker can't see the mistake (`rotate()` without an angle). Invalid options are `TypeError`s with `code: 'ERR_INVALID_OPTIONS'` (`invalidOptions()` in `js/protocol.ts`), whichever side finds them.
- Images are always 8-bit `Luma8`/`LumaA8`/`Rgb8`/`Rgba8` after `decode::normalize`.
- Rely on the worker's memory limits and the caller's timeout, instead of configuring each decoder defensively. Only the pixel limit is checked up front. Anything allocated outside Rust (libwebp, mozjpeg) needs its own check against `Limits`.
- Workers are untrusted. The JS wrapper validates every response, and kills a worker that sends a malformed one, or output it wasn't asked for. Each worker handles one request at a time, and is replaced after `maxImagesPerWorker` responses (default 1, or 64 for native workers on Windows, where spawning is slow), so a compromised worker can't see later images.
- Workers are built with `panic = "abort"` (the `dev` and `release` profiles; tests ignore it), so there's no `catch_unwind`. A panic, abort, or out-of-memory exit only ends the worker.
- After changing a `#[typeshare]` item, run `pnpm generate` (needs `cargo install typeshare-cli --version 1.13.4 --locked`). The framing and the `Request` enum (externally tagged, which typeshare can't export) aren't generated, so keep `crates/core/src/protocol.rs` and `js/protocol.ts` in sync by hand, and the fork server's messages in `crates/worker/src/fork_server.rs` and `js/native.ts`.
- The worker's version (`Cargo.toml`) must match `package.json`'s, which `js/native.ts` passes it. A worker test checks this. `pnpm set-version` sets both (see "Publishing").
- Tests generate fixtures with sharp. Never commit images. Compare against sharp for parity (dimensions exactly, pixels approximately).
- Before changing CI, read `.github/AGENTS.md` (pinned SHAs, `permissions: {}`, installing pnpm, etc).

## Workers

- **Spawning:** `js/native.ts` spawns workers with `<version> <parent pid> <memory limit>` arguments (the worker exits with `EXIT_VERSION_MISMATCH` if the version differs), an empty environment (except for the seccomp escape hatch, see below), and piped stdin/stdout. The pool is single-threaded JS: it writes each request, reads the response (checking its length against `maxResponseBytes` before allocating it), and kills workers with `child.kill`, which can't hit a reused pid (Node reaps its children on the same thread, and never signals one it reaped).
- **Fork server (unix):** by default (`forkServer` in `PoolOptions`), each pool spawns one worker with `--fork-server`, which forks the pool's workers (skipping `exec` and loading the binary). It talks to the pool over Node's IPC channel (fd 3, `stdio: [..., 'ipc']`), which can pass file descriptors: for each worker, the server creates a socketpair and forks, the worker's stdin and stdout are one end, and the server sends the other to the pool as a `net.Socket`. So there's no socket that another process could connect to. The server takes `spawn` and `kill` messages, and replies with the pid and socket, and after reaping a worker, its exit status (JSON, which the pool doesn't validate, because the server is trusted). Node doesn't support its IPC channel with a process that isn't Node, but the protocol hasn't changed significantly since Node 0.8 (2012), and Bun and Deno use the same one. `node_ipc.rs` implements (and documents) the parts we use. Only the server can kill forked workers safely (it only signals workers it hasn't reaped), so there are no pidfds. Its replies time out (`SERVER_TIMEOUT_MS`), including reaping a worker after `kill`, and the pool kills a server that's stuck (on Linux, that kills its workers too), and starts another. The server is single-threaded and never sees image data, and workers close every fd it holds. The server itself has no seccomp filter (workers install theirs after forking). A filter for it would have to allow everything a worker does before its own filter is on (`clone`/`clone3`, `prctl`, `seccomp`, `dup3`, `rseq`, etc., varying by architecture and libc), for little benefit: it only reads messages from Node, and workers can't reach it. Forked workers share the server's address space layout (ASLR) and stack canaries (documented in the README). The `native worker failures` tests use shell scripts as workers, so they mostly turn the fork server off.
- **Parent death:** on Linux, `PR_SET_PDEATHSIG` kills the worker when the thread that spawned it exits: the JS thread that started it (so a pool created in a `worker_threads` worker loses its workers when that thread exits), or for forked workers, the fork server, which is single-threaded. So the worker is single-threaded too: it reads each request on the main thread, and only notices stdin closing between requests. Elsewhere, there's no `PR_SET_PDEATHSIG`, so a reader thread exits the process as soon as stdin closes, even mid-request. On macOS, that's the only way forked workers end after their fork server exits.
- **seccomp (Linux x86_64/aarch64/riscv64, the architectures seccompiler supports):** after startup, only I/O on existing fds, memory management, futexes, and exiting are allowed. Anything else fails with `EPERM`, except `tgkill` and `tkill` (how `abort` raises `SIGABRT`), which kill the worker with `SIGSYS`, so a compromised worker can't signal Node or the fork server. The filters are built with [seccompiler](https://github.com/rust-vmm/seccompiler)'s Rust API (no `json` feature), and compiled at startup, before forking, so forked workers share them. That's why they can't contain the worker's own pid. There are two, because each seccompiler filter has a single action for the syscalls it matches. They're installed with `TSYNC`, in case a thread is ever started before them (and threads can't be started after them: glibc's thread setup needs `clone3`, `rseq`, and `set_robust_list`). If a decoder starts needing a new syscall, it'll show up as a confusing error, not a crash. If installing the filters fails, the worker exits with `EXIT_SANDBOX_FAILED`, unless `NEXT_SAFE_IMAGE_OPTIMIZATION_DANGEROUSLY_IGNORE_SECCOMP_FAILURES=1` (the only variable `js/native.ts` passes through to workers). That's only for CI's riscv64 tests: QEMU's user mode emulation doesn't support seccomp, so nothing tests the riscv64 filters.
- **Memory limits:** `ExitOnOom` counts live Rust allocations. While a request runs, it exits with `EXIT_MEMORY_LIMIT` (reported as `ERR_LIMIT_EXCEEDED`) if they exceed the request's `limitAllocatorMemoryBytes`, which includes the request buffer itself. Between requests, there's no limit, because the next request is read before its limit is known. libwebp and mozjpeg (C) allocate with `malloc` directly, so only the hard limit sees it: the pool's `limitProcessMemoryBytes`, which the worker applies as `RLIMIT_DATA` at startup (Linux only: macOS's `RLIMIT_DATA` counts reserved address space, so any useful limit fails), or the wasm memory's maximum. When an allocation fails (including `try_reserve`), `ExitOnOom` exits with `EXIT_OUT_OF_MEMORY`. On wasm, exits go through `proc_exit`.
- **Timeouts:** start when a worker picks up a request (not while it's queued). They're JS timers, so a blocked event loop delays them.
- **Aborting and shutdown:** an aborted `signal` removes a queued request, or kills its worker (like a timeout). `Pool.close()` stops accepting requests, finishes the queued and running ones, and resolves once every worker (and the fork server) has exited, holding a ref'd timer meanwhile, since workers are unref'd while idle. `destroy()` fails every request with `ERR_POOL_CLOSED` first. There's no queue limit: that's left to a reverse proxy (`docs/safety.md`).
- **wasm:** each instance runs in its own worker thread, imports its memory (so JS sets the maximum), and is discarded after a trap, `proc_exit`, or timeout.

## Decoders

Memory is bounded by the worker's limits (`limitAllocatorMemoryBytes` in the allocator, `limitProcessMemoryBytes` from the OS), and CPU by the caller's `timeoutMs()`. So decoders aren't configured defensively: the only check before decoding is the pixel limit (`Limits::check_input_pixels`), which works the same way for every format.

Every raster format is detected by `image`'s `ImageReader` (`decode/mod.rs`), from magic bytes. The detected format must be in an explicit allowlist (`InputFormat::from_image_format`): `image` also detects formats like BMP and QOI, and Cargo's feature unification means another crate could enable their decoders. Only if `image` detects nothing do we check for SVG. Then the format is checked against the caller's `allowInputFormats()` (every format except SVG by default, see below). `decode::raster_decoder` constructs the decoder itself (like `ImageReader::into_decoder`, but only for our formats), with `limitAllocatorMemoryBytes` as `image`'s `max_alloc`. With `animated('reject')`, it rejects animations before decoding any pixels, using `PngDecoder::is_apng` and `WebPDecoder::has_animation`, `avif::has_sequence_brand` (avif-parse rejects sequences as unsupported, so this runs first), and `gif::has_second_frame` (`GifDecoder` can only find a second frame by decoding it, so this scans with the `gif` crate, without LZW decoding).

- **JPEG (zune-jpeg), PNG, GIF, WebP, TIFF:** `image`'s built-in decoders. GIF frames always decode as RGBA, so we drop the alpha channel if the first frame is opaque. `image`'s TIFF decoder doesn't support YCbCr, which is how sharp and most encoders write JPEG-compressed TIFFs.
- **AVIF (vendored avif-decode → avif-parse + rav1d):** not `image`'s AVIF decoder, which is dav1d (C). `decode/avif.rs` is an `ImageDecoder` wrapper, and registers a detection hook (checked before `image`'s own signatures, which miss sequences and large `ftyp` boxes). avif-decode is patched with `decode_into`, so it decodes straight into `image`'s buffer, without a copy. rav1d is a git dependency on an unreleased revision for its Rust API. One thread (decoding happens on the calling thread, nothing is spawned on wasm), and the decoded size must match the sequence header. rav1d logs errors to stderr (`rust_api::Settings` can't disable its logger), which release builds discard.
- **SVG (resvg → usvg + tiny-skia):** detected like libvips (`<svg` in the first 1000 bytes, after valid UTF-8). Like sharp, it's rendered at 72 DPI, as RGBA, and at the size it's being resized to (`ops::vector_scale`), not resampled from its natural size. The pixel limit applies to both the natural and rendered sizes. Built without `text` (no fonts at all: Next.js's OG images come from Satori, which converts text to paths) and `svgz`. `raster-images` renders embedded images (`<image href="data:...">`). **The pixel limit doesn't apply to them**: resvg decodes them itself, during rendering, with no size checks, so they're only bounded by the memory limits and the timeout. A small SVG can embed a huge image. That's why SVG isn't allowed by default (`InputFormat::DEFAULT_ALLOWED`). This is documented in `limitInputPixels()`'s and `allowInputFormats()`'s doc comments, `docs/safety.md`, and `docs/sharp.md`, so keep those in sync. usvg's default `<image href>` resolver reads files, so `decode/svg.rs` replaces it with one that only accepts `data:` URLs. On wasm, that dead `std::fs` code still imports WASI filesystem functions, which `js/wasm-worker.ts` stubs out to always fail.

## Encoders

JPEG uses `jpeg-encoder` by default, and mozjpeg (C) with `mozjpeg: true`. mozjpeg's defaults are sharp's mozjpeg preset (trellis quantization, overshoot deringing, scan optimization). It reports errors by unwinding, which aborts the worker, so check anything it would reject (like dimensions over 65500) before encoding.

libwebp and mozjpeg (C) are the only encoders the allocator can't see, so `encode::c_encoder_bytes_per_pixel` estimates their working memory, and checks it against `limitAllocatorMemoryBytes` before encoding. The numbers are measured (peak RSS on noisy 16 MP images), so re-measure when changing their settings.

## Gotchas

- **wasm:** wasi-sdk only compiles libwebp and mozjpeg. Rust links with its own bundled wasi-libc. Rust 1.100+ links wasi-libc's reactor startup (an `_initialize` export) and older versions don't, so `js/wasm-worker.ts` calls `_initialize` only if it exists.
- **Linux CI:** builds use cargo-zigbuild (`-x`). `scripts/build-native.mjs` adds a `.2.28` suffix to gnu targets, which sets the glibc version (matching Node), instead of zig's default. On Linux, `js/native.ts` prefers the gnu worker, unless Node itself uses musl, and falls back to the musl one (it's static, so it runs anywhere).
- **riscv64 CI** (glibc only, like sharp) runs the tests under QEMU's user mode emulation, in a Debian container with an unofficial Node.js build (official ones don't include riscv64). QEMU doesn't support seccomp, so workers ignore failing to install their filters (see "seccomp"), and silently ignores `RLIMIT_DATA` (it would limit QEMU's own allocations), so `NSIO_TEST_QEMU=1` skips the `limitProcessMemoryBytes` test. On riscv, rav1d needs an unstable feature (`stdarch_riscv_feature_detection`), so `scripts/build-native.mjs` sets `RUSTC_BOOTSTRAP=rav1d`.
- **CI artifacts** don't keep file permissions, so test jobs `chmod +x` the worker, and `scripts/pack-npm.mjs` sets its mode in the packages.

## Publishing

Every package has the same version: `pnpm set-version <version>` (`scripts/set-version.mjs`) sets it in `package.json`, `Cargo.toml`, and `Cargo.lock`, in a PR. Then the `Release` workflow (`.github/workflows/release.yml`, run by hand from `main`) runs `build_and_test.yml` (as a reusable workflow), packs its artifacts, publishes them, and creates the GitHub release and `v<version>` tag. Its `dry-run` input only packs and tests the packages (from any branch).

- **Packages:** `scripts/pack-npm.mjs` packs `@next/safe-image-optimization` (`dist/`), `@next/safe-image-optimization-<platform>` (the worker for each target in `scripts/platforms.mjs`, which must match `build_and_test.yml`'s, with `os`, `cpu`, and `libc` fields), and `@next/safe-image-optimization-wasm32` into `npm/*.tgz`. The platform packages are the main package's `optionalDependencies`, which only exist in its packed `package.json`: in the repo's, `pnpm install --frozen-lockfile` would need them to be published already. `scripts/test-npm-packages.mjs` installs the tarballs, and processes an image with the native and wasm backends (`scripts/installed-package-test.cjs`).
- **Third-party notices:** the binaries' packages include `THIRD-PARTY-NOTICES.txt`: the crates' license texts from [cargo-about](https://github.com/EmbarkStudios/cargo-about) (`about.toml`, `about.hbs`), the same for every package (every target's crates, including proc macros), plus Rust's standard library and the libc that some targets link statically (`scripts/licenses/`). `accepted` picks the simplest of a crate's alternatives (MIT over Apache-2.0), and the template leaves out licenses that don't require a notice in binaries (Zlib, CC0-1.0, Unlicense, 0BSD). cargo-about fails for licenses that aren't accepted. Crates whose source files have license headers (or whose license file isn't their whole license) need a `clarify` entry, pinned by checksum, or each header becomes a notice. A stale checksum is only a cargo-about warning, so `scripts/third-party-notices.mjs` fails on warnings. To install cargo-about locally: `cargo install cargo-about --version 0.9.3 --locked`.
- **npm:** `scripts/publish-npm.mjs` publishes the tarballs with `pnpm publish`, the main package last, and skips versions that are already published, so a failed release can be rerun. The dist-tag is `latest`, or a prerelease's identifier (like `canary`). Only the workflow's `publish` job can publish, with npm's trusted publishing (OIDC, configured for each package on npmjs.com: this repository, `release.yml`, and the `npm` environment), so there's no npm token, and the packages have provenance.
