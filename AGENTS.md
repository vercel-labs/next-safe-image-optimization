# AGENTS.md

A safer replacement for sharp in Next.js: decode (untrusted) → auto-orient/rotate → resize → blur → encode. A sharp-like TypeScript wrapper sends each image to a pool of workers: native worker processes (managed by a small napi-rs binding), or worker threads running a wasm build.

## Layout

A Cargo workspace:

- `crates/core` (`blunt-core`): everything that touches images. Only ever runs in a worker.
  - `protocol.rs`: the request/response format (the other side is `js/protocol.ts`), and worker exit codes. `request.rs`: request options, validated again (the JS wrapper isn't a security boundary).
  - `pipeline.rs`: stage order. Resizes *before* rotating (cheaper), so `orientation.rs` maps targets and gravity back to the input frame. ICC → sRGB (`color.rs`, moxcms) runs after resizing.
  - `decode/`: one file per format. `encode/`: one file per format. `ops.rs`: resize (fast_image_resize), embed, blur.
  - `limits.rs`: memory limits. `alloc.rs`: `ExitOnOom`, the workers' global allocator.
- `crates/worker` (`blunt-image-optimization-worker`): the worker process. Reads requests from stdin, writes responses to stdout. Sandboxed with seccomp on Linux.
- `crates/wasm`: the same, as a `wasm32-wasip1` module with raw exports (no wasm-bindgen, no napi).
- `crates/shim`: the napi binding. Only spawns and talks to workers, with no image code. One driver thread per live worker, plus a watchdog thread for timeouts.
- `vendor/avif-decode/`: git subtree of [avif-decode](https://github.com/kornelski/avif-decode), patched to disable rav1d's asm, use rav1d's Rust API, and take thread and frame size options. Commit upstream updates with `git subtree pull --squash`.
- `js/index.ts`: public API (compiled to `dist/` by `pnpm build:js`). `js/native.ts` and `js/wasm.ts` are the two backends, and `js/wasm-worker.ts` runs in each wasm worker thread.
- `binding.js`, `binding.d.ts`: generated by napi, but committed. CI fails if they're stale.
- `test/*.test.ts`: e2e tests (`node --test`, native type stripping).
- `scripts/build-native.mjs`: builds the shim (with `napi build`, in a scratch directory) and the worker, and copies them to the root.
- `scripts/build-wasm.mjs`: builds the wasm module, and checks its imports against an allowlist (the stubs in `js/wasm-worker.ts`).

## Rules

- Never decode with C libraries. libwebp is only for encoding.
- Disable `default-features` and enable exact features for dependencies.
- Import with `crate::` paths, not `super::`. The only exception is `use super::*;` in `mod tests`.
- Images are always 8-bit `Luma8`/`LumaA8`/`Rgb8`/`Rgba8` after `decode::normalize`.
- Every allocation sized by input must be checked against `Limits` first. The pool's timeout and the worker boundary are a backstop, not a substitute: they turn a hang or crash into an error, but the limits give useful errors and keep workers alive.
- Bound CPU work with input-proportional limits (like `max_scans`). Wall-time timeouts are per request, and kill the worker.
- Workers are untrusted. The shim and the JS wrapper validate every response, and kill a worker that sends a malformed one. Each worker handles one request at a time.
- Workers are built with `panic = "abort"` (the `worker` and `worker-dev` profiles), so there's no `catch_unwind`. A panic, abort, or out-of-memory exit only ends the worker. Keep `crates/shim` panic-free: it runs inside Node.
- Exit codes and the protocol are duplicated in `crates/core/src/protocol.rs`, `crates/shim/src/pool.rs`, and `js/protocol.ts`. Keep them in sync.
- Tests generate fixtures with sharp. Never commit images. Compare against sharp for parity (dimensions exactly, pixels approximately).
- Before changing CI, read `.github/AGENTS.md` (pinned SHAs, `permissions: {}`, corepack, etc).

## Workers

- **Spawning:** the shim spawns workers with `<version> <parent pid>` arguments (the worker exits with `EXIT_VERSION_MISMATCH` if the version differs), an empty environment, and piped stdin/stdout. stderr is inherited in debug builds, and discarded in release builds.
- **Parent death:** a reader thread in the worker exits the process as soon as stdin closes, even mid-request. On Linux, `PR_SET_PDEATHSIG` also kills the worker when its driver thread exits, so the driver must outlive its worker.
- **seccomp (Linux x86_64/aarch64):** after startup, only I/O on existing fds, memory management, futexes, and aborting are allowed. Anything else fails with `EPERM`. The filter uses `TSYNC`, after the reader thread has started (glibc's thread setup needs `rseq` and `set_robust_list`). If a decoder starts needing a new syscall, it'll show up as a confusing error, not a crash.
- **Memory limits:** `ExitOnOom` counts live Rust allocations. While a request runs, it exits with `EXIT_MEMORY_LIMIT` (reported as `ERR_LIMIT_EXCEEDED`) if they exceed the request's `limitAllocatorMemory`, which includes the request buffer itself. Between requests, there's no limit, because the next request is read before its limit is known. libwebp (C) allocates with `malloc` directly, so only the hard limit sees it: the pool's `limitProcessMemory`, which the worker applies as `RLIMIT_DATA` at startup (Linux; macOS doesn't enforce it), or the wasm memory's maximum. When an allocation fails (including `try_reserve`), `ExitOnOom` exits with `EXIT_OUT_OF_MEMORY`. On wasm, exits go through `proc_exit`.
- **Timeouts:** start when a worker picks up a request (not while it's queued). The watchdog kills the worker, which also unblocks the driver's pipe I/O.
- **wasm:** each instance runs in its own worker thread, imports its memory (so JS sets the maximum), and is discarded after a trap, `proc_exit`, or timeout.

## Why decoders are called directly

`image` doesn't expose these options, so decoders are called directly:

- **JPEG (zune-jpeg):** sets `max_scans` to 32 (default 100; each progressive scan is a full pass). A pre-scan counts raw `FF E1` byte pairs and rejects more than 4096, because zune's extended-XMP reassembly is O(n²). It counts raw bytes rather than parsing segments, so it can't disagree with zune's parser. Memory checks include progressive (or multi-scan) DCT coefficient buffers.
- **PNG:** `image` uses the full allocation budget as png's metadata limit, so a small iCCP chunk could inflate to 512 MiB. We cap metadata at 16 MiB, skip text chunks, and use `STRIP_16`.
- **GIF:** `check_frame_consistency(true)`. Otherwise a 1x1 screen can hold a 65535x65535 frame.
- **WebP:** `set_memory_limit`. Otherwise metadata chunks are allocated from declared sizes (up to 4 GiB). image-webp limits-checks the VP8X canvas, but allocates from the VP8/VP8L/ANMF frame headers, so we check that the first frame matches the canvas. Known gap: VP8L Huffman tables aren't bounded.
- **AVIF (vendored avif-decode → avif-parse + rav1d):** rav1d is a git dependency on an unreleased revision for its Rust API. Its `dav1d_*` C API is `extern "C"`, so a panic there (rav1d panics on some invalid input) aborts, which only ends the worker. One thread (decoding happens on the calling thread, nothing is spawned on wasm), `frame_size_limit` from the sequence header, and the decoded size must match it. A pre-scan walks the OBUs the way rav1d does and rejects more than 8 frame headers per item: each frame (even a few-byte `show_existing_frame`) is a full decode. Known gap: avif-parse pre-allocates from declared box sizes and entry counts (bounded only by `try_reserve`, which now exits the worker). rav1d logs errors to stderr (`rust_api::Settings` can't disable its logger), which release builds discard.
- **TIFF:** still decoded through `image`. A pre-scan rejects JPEG compression (6/7): each tile gets an unbounded JPEG decoder, and tiles can share one tiny JPEG. It also checks tile area against the memory limit.

## Encoders

`encode::bytes_per_pixel` estimates each encoder's working memory. The numbers are measured (peak RSS on noisy 16 MP images), so re-measure when changing encoders or their settings.


## Gotchas

- **wasm:** wasi-sdk only compiles libwebp. Rust links with its own bundled wasi-libc. Rust 1.100+ links wasi-libc's reactor startup (an `_initialize` export) and older versions don't, so `js/wasm-worker.ts` calls `_initialize` only if it exists.
- **Linux CI:** builds use cargo-zigbuild (glibc 2.28, matching Node), for both the shim and the worker.
- **CI artifacts** don't keep file permissions, so test jobs `chmod +x` the worker.
- **Publishing:** the worker belongs in each platform package, next to the `.node` file (`js/native.ts` looks there), but `napi prepublish` doesn't know about it yet.
