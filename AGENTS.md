# AGENTS.md

A safer replacement for sharp in Next.js: decode (untrusted) → auto-orient/rotate → resize → encode. A sharp-like TypeScript wrapper sends each image to a pool of workers: native worker processes (spawned by the wrapper, with `node:child_process`), or worker threads running a wasm build. There's no native Node addon.

## Layout

A Cargo workspace:

- `crates/core` (`blunt-core`): everything that touches images. Only ever runs in a worker.
  - `protocol.rs`: the request/response format (the other side is `js/protocol.ts`), and worker exit codes. Both are JSON plus binary data (the input, or the encoded image), in a frame with the JSON's length. A response's JSON is at most `MAX_JSON_BYTES` (the worker truncates long error messages), and its data at most the request's `limitOutputBytes`, so the parent knows how much it may have to buffer. `request.rs`: request options. The JS wrapper passes most of them through as the caller wrote them, so this is where they're validated, including unknown fields. The wrapper throws its errors (`ERR_INVALID_OPTIONS`) as `TypeError`s. Items marked `#[typeshare]` (request options, responses, `InputFormat`, `ErrorCode`, and constants) are exported to `js/protocol.generated.ts`.
  - `pipeline.rs`: stage order. Resizes *before* rotating (cheaper), so `orientation.rs` maps targets back to the input frame (crops are always centered, so they're the same in either frame). ICC → sRGB (`color.rs`, moxcms) runs after resizing.
  - `decode/`: one file per format. `encode/`: one file per format. `ops.rs`: resize (`image::imageops`, with alpha premultiplied around it). Only what Next.js uses: sharp's default `fit: 'cover'` (centered), plus `kernel`, `withoutEnlargement`, and `withoutReduction`.
  - `limits.rs`: memory limits. `alloc.rs`: `ExitOnOom`, the workers' global allocator.
- `crates/worker` (`blunt-image-optimization-worker`): the worker process. Reads requests from stdin, writes responses to stdout. Sandboxed with seccomp on Linux. With `--fork-server` (unix), it forks workers instead (`fork_server.rs`), and passes their sockets to Node over its IPC channel (`node_ipc.rs`).
- `crates/wasm`: the same, as a `wasm32-wasip1` module with raw exports (no wasm-bindgen).
- `vendor/avif-decode/`: git subtree of [avif-decode](https://github.com/kornelski/avif-decode), patched to disable rav1d's asm, use rav1d's Rust API, and take thread and frame size options. Commit upstream updates with `git subtree pull --squash`.
- `js/index.ts`: public API (compiled to `dist/` by `pnpm build:js`). `js/native.ts` and `js/wasm.ts` are the two backends, and `js/wasm-worker.ts` runs in each wasm worker thread. `js/musl.ts` is copied from napi-rs (MIT, with its license header).
- `js/protocol.generated.ts`: generated by [typeshare](https://github.com/1Password/typeshare) (`pnpm generate`, configured by `typeshare.toml`), but committed. CI fails if it's stale. typeshare exports unit enums as TS enums, so `js/index.ts` derives the public string unions from them (`` `${generated.Fit}` ``), and `typeshare.toml` maps fields to those unions too. It can't export externally tagged enums (`Request`) or string constants.
- `test/*.test.ts`: e2e tests (`node --test`, native type stripping).
- `turbo.json`: `pnpm build` and `pnpm build:release` run the native and JS builds in parallel with turbo, which caches `build:js` (cargo caches the native and wasm builds itself). Builds default to debug; only scripts suffixed with `:release` produce release builds. CI runs build tasks through turbo.
- `scripts/build-native.mjs`: builds the worker, and copies it to the root as `blunt-image-optimization-worker.<platform>` (Node's platform name, like `linux-x64-gnu`), where `js/native.ts` looks for it before the platform's package. Local builds show the worker's stderr, and installed ones discard it.
- `scripts/build-wasm.mjs`: builds the wasm module, and checks its imports against an allowlist (the stubs in `js/wasm-worker.ts`).

## Rules

- Never decode with C libraries. libwebp and mozjpeg are only for encoding.
- Disable `default-features` and enable exact features for dependencies.
- Never ship two copies of an image library. resvg decodes embedded images with its own direct dependencies on zune-jpeg, png (via tiny-skia), gif, and image-webp, which must resolve to the same versions as `image`'s. When upgrading `image` or resvg, upgrade the other to match. `decode::svg::tests::image_crates_are_deduplicated` checks `Cargo.lock`.
- Import with `crate::` paths, not `super::`. The only exception is `use super::*;` in `mod tests`.
- The API is loosely based on sharp's, but sharp compatibility is a rough guideline, not a rule. Prefer clearer names (with units, like `timeoutMs()` and `limitOutputBytes`) and a smaller API over matching sharp.
- Validate options in `request.rs`, not in `js/index.ts`, unless the wrapper uses them itself (pool options, `timeoutMs()`, `limitOutputBytes`).
- Images are always 8-bit `Luma8`/`LumaA8`/`Rgb8`/`Rgba8` after `decode::normalize`.
- Rely on the worker's memory limits and the caller's timeout, instead of configuring each decoder defensively. Only the pixel limit is checked up front. Anything allocated outside Rust (libwebp, mozjpeg) needs its own check against `Limits`.
- Workers are untrusted. The JS wrapper validates every response, and kills a worker that sends a malformed one, or output it wasn't asked for. Each worker handles one request at a time.
- Workers are built with `panic = "abort"` (the `worker` and `worker-dev` profiles), so there's no `catch_unwind`. A panic, abort, or out-of-memory exit only ends the worker.
- After changing a `#[typeshare]` item, run `pnpm generate` (needs `cargo install typeshare-cli --version 1.13.4 --locked`). The framing and the `Request` enum (externally tagged, which typeshare can't export) aren't generated, so keep `crates/core/src/protocol.rs` and `js/protocol.ts` in sync by hand, and the fork server's messages in `crates/worker/src/fork_server.rs` and `js/native.ts`.
- The worker's version (`Cargo.toml`) must match `package.json`'s, which `js/native.ts` passes it. A worker test checks this.
- Tests generate fixtures with sharp. Never commit images. Compare against sharp for parity (dimensions exactly, pixels approximately).
- Before changing CI, read `.github/AGENTS.md` (pinned SHAs, `permissions: {}`, corepack, etc).

## Workers

- **Spawning:** `js/native.ts` spawns workers with `<version> <parent pid> <memory limit>` arguments (the worker exits with `EXIT_VERSION_MISMATCH` if the version differs), an empty environment, and piped stdin/stdout. The pool is single-threaded JS: it writes each request, reads the response (checking its length against `maxResponseBytes` before allocating it), and kills workers with `child.kill`, which can't hit a reused pid (Node reaps its children on the same thread, and never signals one it reaped).
- **Fork server (unix):** by default (`forkServer` in `NativeOptions`), each pool spawns one worker with `--fork-server`, which forks the pool's workers (skipping `exec` and loading the binary). It talks to the pool over Node's IPC channel (fd 3, `stdio: [..., 'ipc']`), which can pass file descriptors: for each worker, the server creates a socketpair and forks, the worker's stdin and stdout are one end, and the server sends the other to the pool as a `net.Socket`. So there's no socket that another process could connect to. The server takes `spawn` and `kill` messages, and replies with the pid and socket, and after reaping a worker, its exit status (JSON, which the pool doesn't validate, because the server is trusted). Node doesn't support its IPC channel with a process that isn't Node, but the protocol hasn't changed significantly since Node 0.8 (2012), and Bun and Deno use the same one. `node_ipc.rs` implements (and documents) the parts we use. Only the server can kill forked workers safely (it only signals workers it hasn't reaped), so there are no pidfds. Its replies time out (`SERVER_TIMEOUT_MS`), including reaping a worker after `kill`, and the pool kills a server that's stuck (on Linux, that kills its workers too), and starts another. The server is single-threaded and never sees image data, and workers close every fd it holds. The server itself has no seccomp filter (workers install theirs after forking). A filter for it would have to allow everything a worker does before its own filter is on (`clone`/`clone3`, `prctl`, `seccomp`, `dup3`, `rseq`, etc., varying by architecture and libc), for little benefit: it only reads messages from Node, and workers can't reach it. Forked workers share the server's address space layout (ASLR) and stack canaries (documented in the README). The `native worker failures` tests use shell scripts as workers, so they mostly turn the fork server off.
- **Parent death:** a reader thread in the worker exits the process as soon as stdin closes, even mid-request. On Linux, `PR_SET_PDEATHSIG` also kills the worker when the thread that spawned it exits: the JS thread that started it (so a pool created in a `worker_threads` worker loses its workers when that thread exits), or for forked workers, the fork server, which is single-threaded.
- **seccomp (Linux x86_64/aarch64):** after startup, only I/O on existing fds, memory management, futexes, and aborting are allowed. `tgkill` (for glibc's `abort`) is only allowed on the worker's own pid, so a compromised worker can't signal Node or the fork server. Anything else fails with `EPERM`. The filter uses `TSYNC`, after the reader thread has started (glibc's thread setup needs `rseq` and `set_robust_list`). If a decoder starts needing a new syscall, it'll show up as a confusing error, not a crash.
- **Memory limits:** `ExitOnOom` counts live Rust allocations. While a request runs, it exits with `EXIT_MEMORY_LIMIT` (reported as `ERR_LIMIT_EXCEEDED`) if they exceed the request's `limitAllocatorMemoryBytes`, which includes the request buffer itself. Between requests, there's no limit, because the next request is read before its limit is known. libwebp and mozjpeg (C) allocate with `malloc` directly, so only the hard limit sees it: the pool's `limitProcessMemoryBytes`, which the worker applies as `RLIMIT_DATA` at startup (Linux only: macOS's `RLIMIT_DATA` counts reserved address space, so any useful limit fails), or the wasm memory's maximum. When an allocation fails (including `try_reserve`), `ExitOnOom` exits with `EXIT_OUT_OF_MEMORY`. On wasm, exits go through `proc_exit`.
- **Timeouts:** start when a worker picks up a request (not while it's queued). They're JS timers, so a blocked event loop delays them.
- **wasm:** each instance runs in its own worker thread, imports its memory (so JS sets the maximum), and is discarded after a trap, `proc_exit`, or timeout.

## Decoders

Memory is bounded by the worker's limits (`limitAllocatorMemoryBytes` in the allocator, `limitProcessMemoryBytes` from the OS), and CPU by the caller's `timeoutMs()`. So decoders aren't configured defensively: the only check before decoding is the pixel limit (`Limits::check_input_pixels`), which works the same way for every format.

Every raster format is detected by `image`'s `ImageReader` (`decode/mod.rs`), from magic bytes. The detected format must be in an explicit allowlist (`InputFormat::from_image_format`): `image` also detects formats like BMP and QOI, and Cargo's feature unification means another crate could enable their decoders. Only if `image` detects nothing do we check for SVG. Then the format is checked against the caller's `allowedInputFormats`. `decode::raster_decoder` constructs the decoder itself (like `ImageReader::into_decoder`, but only for our formats), with `limitAllocatorMemoryBytes` as `image`'s `max_alloc`. With `allowAnimated: false`, it rejects animations before decoding any pixels, using `PngDecoder::is_apng` and `WebPDecoder::has_animation`, `avif::has_sequence_brand` (avif-parse rejects sequences as unsupported, so this runs first), and `gif::has_second_frame` (`GifDecoder` can only find a second frame by decoding it, so this scans with the `gif` crate, without LZW decoding).

- **JPEG (zune-jpeg), PNG, GIF, WebP, TIFF:** `image`'s built-in decoders. GIF frames always decode as RGBA, so we drop the alpha channel if the first frame is opaque. `image`'s TIFF decoder doesn't support YCbCr, which is how sharp and most encoders write JPEG-compressed TIFFs.
- **AVIF (vendored avif-decode → avif-parse + rav1d):** not `image`'s AVIF decoder, which is dav1d (C). `decode/avif.rs` is an `ImageDecoder` wrapper, and registers a detection hook (checked before `image`'s own signatures, which miss sequences and large `ftyp` boxes). avif-decode is patched with `decode_into`, so it decodes straight into `image`'s buffer, without a copy. rav1d is a git dependency on an unreleased revision for its Rust API. One thread (decoding happens on the calling thread, nothing is spawned on wasm), and the decoded size must match the sequence header. rav1d logs errors to stderr (`rust_api::Settings` can't disable its logger), which release builds discard.
- **SVG (resvg → usvg + tiny-skia):** detected like libvips (`<svg` in the first 1000 bytes, after valid UTF-8). Like sharp, it's rendered at 72 DPI, as RGBA, and at the size it's being resized to (`ops::vector_scale`), not resampled from its natural size. The pixel limit applies to both the natural and rendered sizes. Built without `text` (no fonts at all: Next.js's OG images come from Satori, which converts text to paths) and `svgz`. `raster-images` renders embedded images (`<image href="data:...">`). **The pixel limit doesn't apply to them**: resvg decodes them itself, during rendering, with no size checks, so they're only bounded by the memory limits and the timeout. A small SVG can embed a huge image. This is documented in `limitInputPixels`'s doc comment and the README, so keep those in sync. usvg's default `<image href>` resolver reads files, so `decode/svg.rs` replaces it with one that only accepts `data:` URLs. On wasm, that dead `std::fs` code still imports WASI filesystem functions, which `js/wasm-worker.ts` stubs out to always fail.

## Encoders

JPEG uses `jpeg-encoder` by default, and mozjpeg (C) with `mozjpeg: true`. mozjpeg's defaults are sharp's mozjpeg preset (trellis quantization, overshoot deringing, scan optimization). It reports errors by unwinding, which aborts the worker, so check anything it would reject (like dimensions over 65500) before encoding.

libwebp and mozjpeg (C) are the only encoders the allocator can't see, so `encode::c_encoder_bytes_per_pixel` estimates their working memory, and checks it against `limitAllocatorMemoryBytes` before encoding. The numbers are measured (peak RSS on noisy 16 MP images), so re-measure when changing their settings.

```sh
WASI_SDK_PATH=... pnpm build:wasm && pnpm test:wasm
```

## Gotchas

- **wasm:** wasi-sdk only compiles libwebp and mozjpeg. Rust links with its own bundled wasi-libc. Rust 1.100+ links wasi-libc's reactor startup (an `_initialize` export) and older versions don't, so `js/wasm-worker.ts` calls `_initialize` only if it exists.
- **Linux CI:** builds use cargo-zigbuild (`-x`). `scripts/build-native.mjs` adds a `.2.28` suffix to gnu targets, which sets the glibc version (matching Node), instead of zig's default. On Linux, `js/native.ts` prefers the gnu worker, unless Node itself uses musl, and falls back to the musl one (it's static, so it runs anywhere).
- **CI artifacts** don't keep file permissions, so test jobs `chmod +x` the worker.
- **Publishing** isn't set up yet. The worker belongs in a package per platform, named `blunt-image-optimization-<platform>` (`js/native.ts` looks there), as optional dependencies of the main package.
